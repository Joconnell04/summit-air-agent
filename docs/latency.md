# Latency budget

How long a caller waits for the agent to start answering, split by stage, so every millisecond has an owner and each stage is measured on every call. The targets are spec S-36: a median under 1.2 s on plain turns and under 2.5 s on turns with a lookup or booking, measured from the moment the caller stops speaking to the first sound of the reply, on real phone audio. Targets are revisited whenever Jackson flags a delay (docs/later.md). Every value marked ASSUMED is replaced with a measured one after the first real calls; until then this page is a plan, not a result.

## Plain turn (no tool call)

| Stage | Budget | Basis |
|---|---|---|
| Phone network in and out (Twilio, SIP trunk to LiveKit) | 150 ms | ASSUMED; measured on the first real calls |
| Deciding the caller has finished (turn detection) | 400 ms | MEASURED 0.35 to 0.6 s on the earlier practice agent (from-other-projects/bobert/latency-notes.md) |
| Final transcript (Deepgram) | runs alongside turn detection | MEASURED 0.2 to 0.4 s after speech ends, same source |
| Model's first words (Claude Haiku, thinking off) | 500 ms | ASSUMED for Haiku 5.5; Haiku 4.5 measured about 1.0 s to first audio end to end, same source |
| First audio from the voice (Cartesia) | 150 ms | ASSUMED; measured on the first real calls |
| **Total** | **about 1.2 s** | |

## Turn with a lookup or booking

| Stage | Budget | Basis |
|---|---|---|
| Plain turn up to the model deciding to call a tool | 1.0 s | as above, without the voice |
| Tool on our server (cached slots, local database) | 100 ms | ASSUMED; the mock answers in 1 to 16 ms (MEASURED, Postman run) |
| A real FSM call, when one is needed | 300 to 800 ms | ASSUMED; avoided on most turns by the lookup before hello and the slot cache |
| Model's second hop (reads the tool result, starts the reply) | 500 ms | ASSUMED |
| First audio | 150 ms | ASSUMED |
| **Total** | **about 1.8 s, up to 2.5 s with an FSM call** | MEASURED 2.3 s on the earlier practice agent |

## Where the time is saved

- **Lookup before hello** and **cached slots** remove most FSM round trips from the conversation (docs/decisions/05-pipeline-and-models.md, the harness).
- **Short tool results** with a ready-to-say sentence keep the second model hop short.
- **Digits:** when the agent has just asked for a phone number or ZIP, it waits a little longer before deciding the caller has finished, because people pause between groups of digits; the earlier practice agent lowered the cap to 1.5 s with 0.35 s of silence (MEASURED).
- **A short bridge line, only for slow tools.** If a tool hasn't answered within about 0.7 s, the agent says one short line ("Okay, let me check that now", "One sec, pulling up the schedule") while it waits, so the caller hears something instead of silence. Rules:
  - Fast tools never trigger it, so most turns go straight to the answer.
  - At most once every few turns, and never the same line twice in a call.
  - The line is pre-recorded audio played by the server, not generated by the model. The earlier practice agent had the model say "one moment" as its own reply, which pushed the real answer back 7 to 10 s (MEASURED); playing a clip alongside the tool call avoids that.
  - Measured in the live pass: kept only if it shortens how long the caller hears nothing.
- **Thinking off** on every live profile (config/models.yaml).

## On-prem option (a possible upsell)

For a client who wants every last bit of speed: running the ears (speech-to-text) and the voice (text-to-speech) on a GPU server in the same building or data center as the phone line, instead of calling Deepgram and Cartesia over the internet, removes two network round trips per reply.

- **Saves:** about 0.1 to 0.2 s per reply (ASSUMED; network hops to US-East providers are typically 20 to 60 ms each way, plus provider queueing).
- **Costs:** about $1,000 to $1,500 a month to rent a suitable GPU server, or about $10,000 to $15,000 to buy one, plus enterprise self-hosting licenses from Deepgram and Cartesia, which are quote-only (ASSUMED; needs vendor quotes).
- **Moving the brain on-prem too** would save maybe another 0.1 to 0.3 s, but means replacing Claude with an open model the client hosts, which costs answer quality; not recommended.
- **Verdict:** worth it only for a very large call volume or a client with a hard data-residency rule; for Summit Air the cloud setup is fast enough.

## How it's measured

Every turn writes timestamps to the call trace: caller stopped, turn end decided, final transcript, model first token, tool start and end, voice first byte, first audio out. `make trace CALL=<id>` prints them per turn, and the live pass reports median and slowest 10% per turn type. The measurement is checked first against a recording with known timings, because the earlier practice agent once blamed 2 to 4 s on speech-to-text that was really a timestamp bug in the harness.

The eval suite records the same stage timings for every scenario (model first token, tool time, second hop; text runs have no phone or voice stages). Each run is compared with the last run of the same suite: any change in median or slowest-10% delay per turn type is printed next to the pass rate and cost, and flagged when it moves more than 100 ms or 10% (ASSUMED threshold). So a new model or prompt that slows the agent down shows up in the same report as one that breaks a test, and in LangSmith next to the earlier run.
