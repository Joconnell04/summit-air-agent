# Tuning knobs

The settings that change how a call feels without changing what the agent does. Each one is named here with the problem it solves, where it lives and how it gets tested, so a complaint from a real call ("it cut me off", "it talks too fast") maps to one setting. Values marked ASSUMED come from the earlier practice agent (Bobert, a personal practice project, not a person; from-other-projects/bobert) and are replaced as they're measured.

| Knob | Problem it solves | Where it lives | Now | How it's tested |
|---|---|---|---|---|
| End-of-turn wait | Slow replies, or the agent answering before the caller has finished | `config/models.yaml` `voice.endpointing` (`normal`, and a longer `digits` wait after asking for a phone number or ZIP) and `voice.vad.min_silence_s` | normal 0.3 to 1.5 s, digits 0.9 to 3.0 s, silence 0.35 s (ASSUMED) | Audio rig: plain-turn median and slowest 10%, plus cut-off and talked-over turns, at the current and shorter values; must-pass safety calls still pass |
| Interruption sensitivity | The agent stopping for a cough or a TV, or not stopping for a real "wait, no" | `voice.interruption` (`min_words`, `min_duration`, false-interruption resume) | 2 words, 0.5 s, resume after 1.5 s (ASSUMED) | Live calls 4 and 5 in evals/live-calls.md; audio rig with noise tracks if a change is needed |
| Reply length cap | Long turns when the prompt slips | The model profile's output-token limit in `config/models.yaml` | not set | Text harness: turn length and grader score at two caps |
| Sampling temperature | Run-to-run variance: stray phrasings, flaky scenarios | The model profile in `config/models.yaml` | not set, so the provider default of 1.0 | Standard suite at 1.0, 0.6 and 0.3, two runs each: pass rate, must-pass, grader score |
| Speaking rate | Callers who can't keep up, especially older callers and anyone hearing an address or number; callers in a hurry | Set per call by the tool server (`app/pace.py`), with steps, bounds and phrases in the tenant's `pace` block (`tenants/summit-air/agent.yaml`); the worker applies it through Cartesia sonic-3's `speed` (0.6 to 2.0, SOURCE: Cartesia API docs via the LiveKit plugin) | 1.0 to start; steps of 0.15 between 0.7 and 1.3 (ASSUMED); 0.85 for an older caller (Jackson, DECISIONS.md 053) | Unit tests (`tests/tool_server/test_ts_pace.py`, `tests/voice/test_voice_pace.py`), the `pace` code check on five eval scenarios (tag `pace`), and a listen on a live call |

## Speaking rate during a call

Built (DECISIONS.md 053). The tool server decides the pace from what the caller says and from its own records; the LiveKit worker only applies the speed it is given. Each call has its own speech session, so one caller's pace never touches another call. Retell sets speed per agent, not per call, so this is our pipeline only.

**What moves it.** The server reads every caller line (`app/pace.py`, called from the turn check in `app/lifecycle.py`):

| What the caller says | What happens | How long it lasts |
|---|---|---|
| Asks to slow down ("can you slow down", "you're talking too fast") | One step slower: 1.0 to 0.85, then 0.7 | The rest of the call, a linked call the same day, and the caller's next call (remembered for their number) |
| Asks to speed up ("you can talk faster", "you're talking so slow") | One step faster: 1.0 to 1.15, then 1.3 | The same as slowing down |
| Asks for normal speed | Back to 1.0, and the remembered pace is cleared | The same |
| Asks to hear the address slower ("say the address slower", or "can you say that again slower?" right after the read-back) | Only the address in the next read-back is one step slower than the call's pace; the words around it, and everything after, stay at the call's pace | The next read-back only |
| "Sorry, what?" twice since the pace last moved | One step slower | The rest of this call; not remembered, since the caller didn't ask |
| Says they're elderly, or gives their own age as 65 or more ("I'm 78") | 0.85, unless the caller has already asked for a pace | The rest of this call and a linked call; not remembered |

Steps are the same size each way, so nothing assumes callers only want slower. The bounds (0.7 to 1.3) sit well inside sonic-3's 0.6 to 2.0; both the step and the bounds are ASSUMED until a listen on real calls. The older-adult line for pace is 65, Jackson's own; priority's older-adult line stays at 60 (DECISIONS.md 019), so a 62-year-old caller is raised in priority but spoken to at the normal pace. Only the caller's own age counts for pace ("my father is 90" doesn't), because the pace is for the person listening; someone else's age still raises priority. Talk about equipment ("the fan is spinning slower", "it heats too slow") is not a request, which is why the phrase lists name the agent or speech and leave out bare "slower" and "too slow".

**Where it lives.** The pace in effect is the call's `call_pace` row; every change is a `pace_changes` row (the turn it followed, the speed, `call` or `address`, and what set it); a remembered pace is `caller_pace`, by tenant and number. All three show in `make trace` and `/debug/calls/{id}`. `/calls/start` returns `pace.speed` to start at (a linked call's, else the remembered one, else 1.0), and every `/calls/{id}/turn` result returns the speed for what the agent says next. When the caller asked, the turn's hints carry `pace_slower`, `pace_faster` or `pace_address`, and `prompts/assemble.py` turns them into a `[server]` note so the agent says a short yes rather than claiming it can't change its voice.

**How the worker applies it.** `voice/livekit/call.py` keeps the speed the server last returned and, in the agent's `tts_node`, calls the Cartesia plugin's `update_options(speed=...)` before each speech starts, because the plugin copies its options when a voice stream opens (read in the plugin source, `livekit-plugins-cartesia`). Every speech, the greeting and the signed-off safety lines included, is spoken at the call's current pace. The pre-recorded clips (the bridge lines and the at-capacity message) stay at their recorded speed. Each agent line is posted with `speed` in its timings, the speed it was actually spoken at, which is what the eval check reads.

**The address alone.** After an address request, the next `read_back` returns the server's sentence in three `parts` with their speeds: the words before the address, the address (one step slower), and the rest. The worker speaks them back to back as written, with no model step, then carries on at the call's pace. Because each part is its own speech, there can be a short gap before and after the address, about the voice's time to first audio (ASSUMED a few hundred milliseconds; listen on a live call). Cartesia's inline speed tags would avoid the gap, but how a tag interacts with the stream's own speed isn't documented, so the parts are the version that can be tested now.

**Tests.** Unit tests for every rule (`tests/tool_server/test_ts_pace.py`), the worker (`tests/voice/test_voice_pace.py`) and the eval check failing when the feature is broken (`tests/tool_server/test_ts_pace_check.py`). Five eval scenarios carry the `pace` tag (`make eval TAGS=pace`): an older caller who gives their age, a caller who asks to slow down, two "sorry, what?", a slower address that then returns, and a caller who asks to speed up. Their `pace` check reads the recorded pace and every agent line's applied speed. All five passed on `livekit` / `fast` (run `20261104-035634-livekit-fast-custom`, $0.14 MEASURED). The must-pass set passed 18 of 19 on the same branch (`20261104-035855-livekit-fast-custom`, $0.40 MEASURED); the miss, `late-correction-after-readback`, was the model paraphrasing the read-back with no pace change on the call, and it passed when run again (`20261104-040012-livekit-fast-custom`).

**Not covered yet.** The text harness can't hear the voice, so whether 0.85 sounds natural, and how long the gap around a slower address is, need a live call. A request the phrase lists miss ("you're rattling that off") isn't heard; the agent can still say it will slow down, but the voice won't change. A model tool that asks the server for a pace change would cover those, validated and recorded by the server; it was left out to keep the tool list as it is until a live call shows the lists are too narrow.
